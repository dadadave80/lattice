# ERC-3643 permissioned token

Lattice's first ERC-3643 profile is a closed immutable composition. It supplies the standard token,
owner-controlled AgentRole, IdentityRegistry, IdentityRegistryStorage, TrustedIssuersRegistry,
ClaimTopicsRegistry and a minimal single-token Compliance component. Its logic is authored fresh
under MIT from the [CC0 standard](https://eips.ethereum.org/EIPS/eip-3643); it does not use GPL T-REX
or ONCHAINID implementation code. Identity and issuer implementations are external ABI peers.

Use `script/base/tokens/DeployERC3643.s.sol` and `ERC3643Params` with the atomic LatticeFactory flow.
The canonical initializer admits only the plain Lattice host, the reviewed facet runtime hashes
and every required selector route. It installs Ownable, ERC-165 and the loupe, with no cut or account
execution route. ERC-7674 temporary approval is the sole optional facet. No upgradeable overload or
caller-supplied facet hash list exists. Admission runs before external component binding and is checked
again after initialization, so callbacks cannot execute an initially unapproved composition.

## Setup and authority

The configuration names the owner, explicit initial agents, name, symbol, decimals and optional token
onchainID. Zero external-component addresses choose the co-located store and compliance. The token
starts paused so identity and compliance setup can finish before ordinary transfers.

```solidity
ERC3643Params memory config;
config.owner = issuer;
config.agents = initialAgents;
config.name = "Permissioned Asset";
config.symbol = "ASSET";
config.decimals = 6;
config.temporaryApproval = true; // Optional ERC-7674, Cancun required.
(FacetCut[] memory cuts, address init, bytes memory data) = recipe.buildCuts(config);
// Supply these to LatticeFactory.deployStrict atomically with a new salt.
```

The owner controls metadata, registry/compliance references, claim topics, trusted issuers, storage
bindings and agent membership. Agents control identity registration, pause, freezes, mint, burn,
forced transfer and recovery. Ownership alone does not make an address an agent. Ownership transfer
changes administrative power immediately and retains existing agents until the new owner removes them.
The suite reuses AccessControl storage internally but does not expose grantRole or advertise IAccessControl.

Register investor identities and countries, configure the required topics and their authorized claim
issuers, bind any external endpoints, then have an agent call `unpause()`. With no required claim
topics, a registered contract identity is verified; an unregistered wallet is never verified. Adding
topics later immediately changes verification. Claim validity is checked on every verification call,
without an eligibility cache. Bad claim candidates fail closed and do not prevent a later valid issuer
from satisfying the same topic.

The co-located minimal Compliance returns true from canTransfer and accepts lifecycle callbacks only
from its bound token. It supplies no country, investor-count, sanctions, holding-period or other
regulatory rule pack. Choose and review an external compliance implementation when those rules are
needed. The owner selects the identity/issuer/compliance trust set; trusted endpoints may deny service
or accept claims according to their own logic.

## Movement rules

| Operation | Pause/full freezes/free balance | Identity requirement | canTransfer | Lifecycle callback |
| --- | --- | --- | --- | --- |
| transfer / transferFrom | Enforced; both wallets must be fully unfrozen | Recipient verified | Enforced | transferred |
| Agent mint | Bypassed | Recipient verified | Bypassed | created |
| Agent forcedTransfer | Bypassed; thaws only the frozen deficit | Recipient verified | Bypassed | transferred |
| Agent burn | Bypassed; thaws only the frozen deficit | None | Bypassed | destroyed |
| Agent recovery | Combines freezes and moves the full balance | Lost identity, target management key and verified target | Bypassed | transferred |

Callbacks observe the completed ledger/freeze effects. A callback failure reverts the entire operation,
including allowance spending and identity changes. The suite's native transient lock rejects reentrant
movement and sensitive configuration/registry mutations, even from an authorized agent. Batch methods
apply their scalar counterpart's rules and revert atomically; batchBurn follows scalar burn's privileged
rules. Ordinary zero-value movements still check pause, freezes, identity and compliance. Approvals
remain available while paused or frozen.

Ordinary transferFrom uses the shared persistent-plus-temporary ERC-20 allowance accounting. Optional
temporary approvals expire at the transaction boundary, consume before persistent approvals, and cannot
bypass permissioned movement checks. The existing IERC20 interface ID and storage remain unchanged.

## Recovery and external bindings

Recovery accepts distinct nonzero old/new wallets, the lost wallet's registered identity, and a target
whose management key is present on that identity. An existing target must have that same identity. A
new target copies the old country; an existing target retains its own country. Partial freezes add,
full freezes combine with OR, the old partial freeze clears, and the old wallet is unregistered and fully
frozen. Zero-balance recovery is allowed. Recovery does not enumerate or revoke either wallet's existing
persistent or same-transaction temporary allowances; the new target's old approvals remain effective.
Consider that authority when choosing a recovery target.

An external identity store must bind the actual registry address. Bind the address returned by
`LatticeFactory.predict(deployer, salt)` before deploying if necessary; counterfactual binding is
deliberately supported. The registry's own address, rather than the EOA owner, performs external writes.
If the token uses an external IdentityRegistry for recovery, that registry must authorize the token
itself as an agent. Co-located operations use internal helpers and preserve the original agent check.

External compliance must already be bound to this token, or genuinely authorize the token to bind it.
Changing compliance also clears the old binding. If only an external owner can unbind, that owner must
clear it out of band before replacement, or grant the token real authority. A failed handshake leaves
the previous binding/reference unchanged. Switching dependencies does not migrate investor records or
policy state.

## Composition and build boundary

The canonical profile rejects every unapproved facet and route, including base ERC20, ERC20Burnable,
ERC1363, ERC20Votes, wrappers, flash mint, crosschain mint/burn, ERC4626/VaultCore/GovernedVault shares,
Pausable, permit conveniences, arbitrary execution and cut facets. This enforces the existing
[movement model](selector-compatibility.md#token-extension-hook-model). An external vault holding this
token as its asset is a different topology and must itself satisfy recipient identity/compliance rules.

`make erc3643-profile-check` compiles canonical solc 0.8.36 / Cancun artifacts and checks the host, all
facets and required selectors against generated initialization-only fingerprints. It rejects linked or
immutable artifacts and facet imports of profile/initializer code. `make erc3643-profile-update`
regenerates after a reviewed source or metadata change; it never updates an existing deployed token.
The release's normal size, interface, storage, gas and security checks still apply.

`version()` is required by ERC-3643 and returns `LatticeVersion.VERSION`, so a Release Please version
change also changes the token's fingerprint. Import the generated version update into reviewed source
preparation, regenerate the profile and freeze those coherent inputs before tagging. The
[release sequence](../../REGISTRY_DEPLOYMENTS.md#prepare-versioned-source-before-freezing-a-release)
keeps CI read-only and avoids publishing stale admission data.

The committed CI gas snapshots use actual diamond routes under Foundry 1.9.0, solc 0.8.36 and
Cancun, excluding setup. Transfer with registered identities and no required claim costs 87,611 gas;
one required claim against the test issuer costs 135,764. Persistent allowance transferFrom costs
89,643, and factory deployment with existing facets and initializer costs 5,619,666, including both
admission checks. These are specific fixtures, not estimates for an external identity or compliance
implementation; [the gas suite](../../test/gas/ERC3643GasTest.t.sol) records the exact setup.

The guarantee assumes the trusted canonical initializer and atomic recipe. LatticeFactory is general:
an arbitrary malicious initializer can always write diamond storage, skip admission or alter state
after a check. ABI resemblance, interface support and a factory address alone do not certify that a
deployment used this profile. There is no global ERC20 hook and no extra movement cost for unrelated
tokens. The profile is immutable; code changes require a new reviewed deployment and an explicit
migration process. See [ADR 0021](../adr/0021-erc3643-closed-immutable-profile.md).
