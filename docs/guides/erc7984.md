# ERC-7984 confidential token

The `ERC7984` module is an ERC-7984 (confidential fungible token) on Zama's FHEVM (fully homomorphic encryption
virtual machine). Balances, transferred amounts and the total supply are handles: 32-byte references to
ciphertexts that Zama's off-chain coprocessors compute on. Zama's access control list (ACL) contract records who
may use or decrypt each handle. Plaintext amounts never appear on chain unless someone with access requests a
public disclosure.

The module follows OpenZeppelin Confidential Contracts 0.5.3, with the deviations and boundary in
[ADR (architecture decision record) 0033](../adr/0033-erc7984-excludes-diamond-callers.md). Host calls go through
the thin `FHEVMLib` of [ADR 0032](../adr/0032-thin-fhevm-host-library.md). The module is pre-release: ERC-7984
is a Draft, and the namespace and interface id freeze once a token is live anywhere.

## Deploy

Two recipes in `script/base/tokens/` build a token. Both deploy atomically through `LatticeFactory`.

| Recipe | Facets | Supply | Upgrade authority |
| --- | --- | --- | --- |
| `DeployERC7984`, default `run(string,string,string)` | `ERC165Facet`, `ERC7984`, `DiamondLoupeFacet` | None: no mint facet | None (immutable) |
| `DeployERC7984`, admin `run(string,string,string,address)` | adds `AccessControl` and `AccessControlDiamondCut` | Only through a mint facet the admin cuts in | The admin, who can therefore decrypt every balance |
| `DeployERC7984Mintable`, `run(address,address,string,string,string)` | `ERC165Facet`, `ERC7984`, `DiamondLoupeFacet`, `AccessControl`, `ERC7984Mintable` | `confidentialMint` by `ERC7984_MINTER_ROLE` | None: no cut facet |

Deploy a mintable token on Sepolia. The arguments are the admin (granted `DEFAULT_ADMIN_ROLE`), the first
minter (granted `ERC7984_MINTER_ROLE`), the name, the symbol and the contract URI. Name the signer explicitly
with `--account`; do not rely on keystore variables in the environment.

```sh
forge script script/base/tokens/DeployERC7984Mintable.s.sol --tc DeployERC7984Mintable \
  --sig "run(address,address,string,string,string)" \
  <admin> <minter> "Confidential Token" "CTKN" "ipfs://<metadata>" \
  --rpc-url sepolia --account <keystore> --broadcast \
  --verify --verifier etherscan --etherscan-api-key "$ETHERSCAN_API_KEY"
```

One `--verify` pass reaches one verifier. To verify on Sourcify too, rerun the same command with `--resume`
and the Sourcify verifier (`--resume --verify --verifier sourcify` in place of the Etherscan flags). If a verification fails, rerun it with `--resume`; never redeploy.

- **Chains.** The recipes support Ethereum mainnet (chain id 1) and Sepolia (11155111). `FHEVMLib` also maps
  chain id 31337 for local tests only: its addresses come from Zama's published example deployer key, so
  anyone with that key can place code there on any network that reuses 31337. Never deploy on a non-local
  network with chain id 31337. Any other chain reverts `FHEVMUnsupportedChain(uint256)`.
- **No supply at initialization.** `ERC7984Init` and `ERC7984MintableInit` write the metadata, the chain's
  coprocessor addresses and the ERC-165 (interface detection) registrations only; `ERC7984MintableInit` also
  writes the two roles. They make no host call and mint nothing. Supply comes afterwards from
  `confidentialMint`, or from a consumer facet.
- **Consumer mint facets.** A facet that mints through `ERC7984Lib._mint` calls `ERC7984Lib.guard()` first,
  enforces that the caller is allowed on any handle it supplies, and passes a freshly computed amount handle
  (for example `FHEVMLib.add(FHEVMLib.asEuint64(0), amount)`) while the supply is uninitialized, because the
  first mint's amount handle becomes the total-supply handle. The same rule binds every burn, wrapper or other
  confidential extension (ADR 0033).
- **Exclusions.** The recipe rule, the initializer's 15-selector deny-list and EIP-7702 (Ethereum Improvement
  Proposal 7702, code delegation for externally owned accounts) host refusal, and the entry guard keep any
  facet that calls or signs as the diamond out of a token diamond. The
  [composition hazards](compose-your-own-diamond.md#composition-hazards) list the refused facets.

The `covers` check compared the holder's ether balance with twice the estimated gas cost. The transfer estimate
stood in for all three holder transactions at first because the sent handle did not yet exist. The request
estimate then covered both remaining transactions. Each send depended on its check passing.

```bash
covers() {
  price=$(cast gas-price --rpc-url sepolia)
  bal=$(cast balance "$HOLDER" --rpc-url sepolia)
  need=$(( $1 * price * 2 ))
  echo "gas $1, price $price wei, need $need wei, balance $bal wei"
  [ "$need" -le "$bal" ] || { echo "STOP: 0.0001 ether does not cover the holder's transactions"; return 1; }
}
```

## Supply without upgrade authority

The diamond is persistently allowed on every handle it stores, and a cut initializer runs as the diamond. So
whoever can cut can decrypt every balance, forever. For a token with supply and no such authority, use
`DeployERC7984Mintable`. It has no cut facet and no facet that calls as the diamond.

- **The admin** (`DEFAULT_ADMIN_ROLE`) can grant and revoke `ERC7984_MINTER_ROLE`, including to itself, so it
  is a supply authority. Renouncing `DEFAULT_ADMIN_ROLE` freezes the minter set. It cannot cut, run code as the
  diamond or change a role's admin, and without the minter role it obtains no ACL grant.
- **A minter** mints any amount to any account except the zero address and the diamond. It is persistently
  allowed on each handle it minted, and obtains no grant on a handle whose value another account determined.

What minters, and the admin after granting itself the minter role, can still learn:

- **Each mint is a supply-threshold bit.** An overflowing mint mints zero, and the minter can decrypt what it
  minted. So a mint of an amount `a` tells it whether the total supply exceeds `2^64-1-a`. An overflowing mint
  changes no balance or supply value, so at most 64 mints recover the supply exactly. When one holder owns most
  of the supply, that approximates the holder's balance.
- **A minter contract can publish the values it minted.** Handles are deterministic per block and name no
  caller. In the same transaction as its own mint, a minter contract can recompute the supply handles its own
  consecutive mints produce (while it is the only account changing the supply) and a never-credited
  recipient's first balance, persist grants on them and request their public disclosure. All are values it
  chose.

For a `DeployERC7984` admin-variant token, the admin is decryption authority until it gives up the cut. Once
supply is minted, end that authority with a final `diamondCut` that removes `AccessControlDiamondCut`'s
`diamondCut` selector (`0x1f931c1c`). Grants made before the cut remain, because ACL grants are irrevocable.

## Integrator rules

These rules are normative. In them, KMS is Zama's key management service, whose signers sign every
decryption; an ERC-1271 validator answers contract signature checks for the diamond; FHE is fully homomorphic
encryption; and HCULimit is Zama's contract that meters homomorphic complexity units (HCU), the per-operation
cost.

1. Always use the returned `transferred` handle. Never assume the requested amount moved.
2. An operator moves an amount it supplies, up to the whole balance; a request above the balance moves zero. It
   can publish what it moved.
3. A receiver holds a persistent grant on `sent` and can publish it at any time. Do not refund manually and also
   return false.
4. De-duplicate `AmountDisclosed`, because it replays. A wrong cleartext or another handle's proof
   reverts the host's `KMSInvalidSigner(address)`; `InvalidKMSSignatures()` means too few valid signers.
5. Never cut an executor, a Governor, a timelock, a cross-chain handler or an ERC-1271 validator into a token
   diamond, and never host the token in an account.
6. Whoever can cut can decrypt everything, forever. `DeployERC7984`'s immutable variant has no
   supply; for supply without that authority, deploy `DeployERC7984Mintable` (no cut facet), or cut
   `AccessControlDiamondCut` away once supply is minted. Its role admin can make any account a minter, so it is
   a supply authority; renouncing `DEFAULT_ADMIN_ROLE` freezes the minter set. Its minters, and its admin after a
   self-grant, can learn the total supply through the overflow bit (at most 64 mints), and a minter contract can
   publish the values it minted, including a never-credited recipient's first balance.
7. Per transaction: at most 22 transfers or 6 transfer-and-calls from one sender, 29 incoming transfers to one
   recipient, and 13 mints per token across all callers, `confidentialMint` included, whether or not the
   supply exists.
8. Liveness depends on Zama: the ACL can be paused, addresses deny-listed, hosts upgraded instantly, and, once
   Zama activates the HCULimit computation allowlist, each diamond address must be admitted before any FHE
   operation.
9. The proof-free overloads need the amount handle allowed to the caller and to the token diamond.
10. Handles are deterministic per block and can be shared across accounts; never key state on a handle or
    compare two handles. Chain id 31337 is supported for local tests only.

## Hazards

These are the accepted hazards. Each is documented, and each that code can exercise is pinned by a test that
fails if the behaviour changes. The hazards the module prevents (co-cut executors, self-call relays, EIP-7702
hosts, ERC-1271 validators, unproven handles, wrong-typed handles, initialization front-running, injected
coprocessor addresses, uninitialized tokens and the diamond as receiver) are in ADR 0033 and the
[composition hazards](compose-your-own-diamond.md#composition-hazards). Hosting the token in an account proxy
is not refused in code: never do it (integrator rule 5).

The token's initialized marker is the `IERC7984` bit in the diamond's ERC-165 map. `ERC6900ModuleManager` writes
ERC-165 bits for every interface id in an installed module's manifest, and the admin or the diamond itself can
install a module. On a hand-built diamond that also installs `ERC6900ModuleManager`, the admin could therefore set
the marker without running `__ERC7984_init`, which skips the deny-list and the EIP-7702 host check, or, after
installing a module before initialization, clear the marker by uninstalling it and brick every guarded entrypoint.
No shipped recipe installs it, and integrator rule 5 forbids it.

## Type identity

`euint64`, `ebool` and `externalEuint64` are user-defined value types over `bytes32`. Lattice vendors their
definitions (`encrypted-types` 0.0.4) at `src/interfaces/external/fhevm/EncryptedTypes.sol`, so Lattice's
`euint64` is a different Solidity type from the one Zama's `FHE.sol` imports. A Solidity consumer that also
uses `FHE.sol` unifies them with one remapping:

```text
encrypted-types/=lib/lattice/src/interfaces/external/fhevm/
```

The ABI (application binary interface) is unaffected: every handle encodes as `bytes32`. The vendored FHEVM
test harness lives in Lattice's `test/helpers/fhevm/` and adds no remapping for projects that install Lattice.

## Batch ceilings

Zama meters every operation in homomorphic complexity units (HCU). At the current depth cap, a transaction
that extends one handle chain too far reverts `HCUTransactionDepthLimitExceeded()` (`0xfc344870`). The ceiling
therefore belongs to the handle chain, not to the sender:

| Handle chain | Per transaction |
| --- | --- |
| One sender's balance | 22 transfers, or 6 transfer-and-calls, whatever the recipients |
| One recipient's balance | 29 incoming transfers from distinct senders |
| The total supply | 13 mints per token, across all callers and recipients |
| No shared chain | 34 transfers, or 14 transfer-and-calls, only when every sender and recipient is distinct |

`confidentialMint` fits 13 per token per transaction in either supply state, and distinct minters share the
same 13. Account-abstraction bundles and `Multicall` batches from different users share the supply chain too.
A future burn extends the same supply chain, so a mix of mints and burns stops sooner. `ERC7984LimitsTest`
pins the 22, 6 and 13 boundaries on the local harness; the 29 and the all-distinct figures are measurements,
not pinned by a local test.

## Handle identity

Handles are deterministic per block. A trivial encryption and every operation result are hashes of the
operation, its operands, the ACL, the chain id, the previous block hash and the timestamp, with no caller and
no counter; only handles from input proofs carry a nonce. So:

- two never-funded senders in the same block get the same encrypted-zero balance handle, and each is allowed on
  the other's;
- anyone who trivially encrypts a public value, such as a plaintext mint amount, in the same block gets the
  same handle and a transient grant on it.

Neither reveals anything, because the value is already public. But never treat a handle as unique to an
account, never key state on a handle and never compare two handles.

## Trust assumptions

A confidential token inherits Zama's protocol. Lattice controls none of the following; see
[`SECURITY.md`](../../SECURITY.md#confidential-tokens-zama-fhevm) for the details.

- **Decryption.** Zama's key management service (KMS) is a 13-node network with a signature threshold of 7.
  Seven colluding or compromised nodes could decrypt any ciphertext.
- **Coprocessors.** Off-chain coprocessors compute every ciphertext operation; the chain records only handles.
- **Upgradeable hosts.** The ACL owner is an Aragon DAO (decentralized autonomous organization) proxy with no
  timelock, so it can upgrade the ACL instantly.
- **Pausing and deny-listing.** A pauser can halt the ACL, which stops every confidential operation (this
  happened once, for 84 minutes on 2026-01-06), and the ACL can deny an address the use of ciphertexts.
- **Computation allowlist.** Zama's HCULimit contract has an allowlist of callers. It is inactive on Sepolia
  and absent on Ethereum mainnet's current host line. Once Zama activates it, a token diamond that Zama has
  not admitted reverts every FHE (fully homomorphic encryption) operation with `CallerNotAllowlisted(address)`.
- **Chain id 31337** is for local tests only (see [Deploy](#deploy)).
